# cacheview repro (.NET 10)

A minimal .NET 10 static-SSR Blazor app (pinned by `global.json` to SDK 10.0.102) showing why caching *part* of a page was awkward before `<CacheView>`. Every page has a "Page rendered at" stamp, a slow `StockSummary` (1.5 s `Task.Delay` standing in for a report query) with a "Figures calculated at" stamp, and a line counting how many times the query ran and how many summary components were created. `/plain` takes 1.5 s on every request. `/memcache` (workaround 1, `IMemoryCache.GetOrCreateAsync` inside the component) is fast on hits, but a new component is still created on every request, and five requests that miss at the same moment run the query five times (no stampede protection). `/wholepage` (workaround 2, `[OutputCache(Duration = 20)]`) is fast, but the page stamp freezes too: everything is cached, all or nothing. `/wholepage-form` adds a form with an `AntiforgeryToken`, so every response carries `Set-Cookie` and `Cache-Control: no-cache, no-store`, and output caching silently stores nothing: back to 1.5 s per request. Run `dotnet run -p:TryNet11Api=true --urls http://localhost:5143` here, then `./probe.sh` in another terminal to print timings, stamps, counters and cache headers for each page. With `-p:TryNet11Api=true` the build also compiles `Components/Probe/Net11Api.razor`, which uses `<CacheView>`: on .NET 10 it does not fail to compile, it only warns `RZ10012: Found markup element with unexpected name 'CacheView'`, and `/cacheview` emits a literal `<CacheView ExpiresAfter=...>` HTML element and stays slow on every request.
