# validatable-type-stable repro (.NET 10.0.102)

This minimal static-SSR Blazor app (pinned to SDK 10.0.102 by its own `global.json`) shows what nested validation looked like in .NET 10. `/plain` uses a model with a nested `AddressForm` and a `List<ContactForm>` but no `[ValidatableType]`: with `Company=Acme`, an empty City, an empty contact name and contact email `sales@`, the POST goes through and `OnValidSubmit` saves (`SAVED company=Acme city='' contactEmail='sales@'`). That is the real failure, and it happens silently. `/marked` is the same model with `[ValidatableType]`. It flags City, Name and Email, and the save never runs. Setting `NO_ADDVALIDATION=1` turns `/marked` back into the silent save. The build variants show the "experimental" story. In a Microsoft.NET.Sdk.Web project, a bare `[ValidatableType]` binds to an SDK-generated internal `Microsoft.Extensions.Validation.Embedded.ValidatableTypeAttribute` (global using) and builds with 0 warnings and no `#pragma`. `-p:DefineConstants=PUBLIC%3BNOPRAGMA` uses the public attribute, which fails with **error** ASP0029 (an error, not a warning). `-p:DefineConstants=PUBLIC` adds the `#pragma` and builds. `-p:DefineConstants=USING` adds `using Microsoft.Extensions.Validation;` (as the .NET 11 demo does), which fails with CS0104 because the reference is ambiguous. To run it: `dotnet build && dotnet run --no-build --urls http://localhost:5788`, then `./post.sh plain` and `./post.sh marked` (this POSTs the form with an antiforgery token and greps out the validation messages and the result line).
