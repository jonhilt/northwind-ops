# server-initiated-circuit-pause repro (.NET 10)

A minimal .NET 10 Blazor Interactive Server app (pinned by `global.json` to SDK 10.0.102): one order form (`Customer`, `Quantity`, both `[PersistentState]`) that shows the server process id and the circuit id, plus two buttons where server code asks the browser to pause through JS interop. The probe `tools/guide-shots/probes/server-initiated-circuit-pause.mjs` starts the server itself and runs four scenarios in Chromium. **A** (the real failure): fill the form, stop the server with SIGTERM and start a new process; the tab shows "Rejoining the server... / Rejoin failed... trying again", then reloads on the new process with an empty form. **B**: the browser calls `Blazor.pauseCircuit()` (a .NET 10 API), the server restarts, Resume brings the form back on a new process and circuit, so pause/resume already survived a restart in .NET 10. **C** and **D**: server code calls `JS.InvokeVoidAsync("Blazor.pauseCircuit")` (awaited, which never returns) or a fire-and-forget `window.remotePause` wrapper (the workaround in dotnet/aspnetcore#62327); both pause the tab with the stock "The session has been paused by the server." dialog and resume with the data intact. So in .NET 10 the server *could* ask a tab to pause, but only from code that holds that circuit's `IJSRuntime`, with a hand-written JS wrapper and no answer about whether it was asked. `Components/Probe/Net11Api.razor` uses the .NET 11 API: build with `dotnet build -p:TryNet11Api=true` to get `CS1061: 'Circuit' does not contain a definition for 'RequestCircuitPauseAsync'`. Run: `dotnet build` here, then `node probes/server-initiated-circuit-pause.mjs` from `tools/guide-shots` (port 5150; Data Protection keys go in `./keys` so a restart can read the paused state).
